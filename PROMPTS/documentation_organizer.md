# 通用项目文档整理 Prompt

复制下面的 Prompt，先填写“项目参数”，再交给 Agent。删除不适用的领域即可；不要删除
编年体、纪传体、验证和 Git 权限规则。

---

## 可复制 Prompt

```text
你现在负责整理和维护一个项目的完整文档体系。请直接阅读项目文件后开展工作，不要只根据
我的描述猜测实现，也不要照抄参考项目。

【项目参数】
- 当前项目路径：<CURRENT_PROJECT_PATH>
- 交接文件：<HANDOFF_FILE_OR_NONE>
- 主要参考项目：<PRIMARY_REFERENCE_PATH_OR_NONE>
- 次要参考项目：<SECONDARY_REFERENCE_PATH_OR_NONE>
- 项目领域：<DOMAIN_1>, <DOMAIN_2>, <DOMAIN_3>
- 本地大资源目录：<LOCAL_RESOURCE_DIR，例如 local/>
- Python 版本/环境：<PYTHON_VERSION_AND_ENV_NAMES>
- 本轮暂缓内容：<DEFERRED_SCOPE_OR_NONE>
- 是否允许修改文件：<YES_OR_NO>
- 是否允许本地 commit：<YES_OR_NO>
- 是否允许 git push：NO，除非我在本次对话中再次明确授权
- 输出语言：中文

【目标】
1. 阅读当前项目、交接文件、现有文档、代码入口、脚本、测试、Git 状态和指定参考项目，
   提炼仍然有效的信息。
2. 建立可长期维护的 Agent 开发知识库，以及独立的、人类可直接操作的教程。
3. 保留有效开发历史，同时保证“当前状态”只有一个，不让旧进展与新实现互相矛盾。
4. 让仓库保持轻量：代码和小型配置进入 Git，大模型、SDK、录制、数据集、日志、构建产物
   和虚拟环境不进入 Git。

【开始前必须检查】
1. 查找并完整阅读 HANDOFF.md、AGENTS.md、README、现有 docs、脚本说明和资源清单。
2. 通过代码、pyproject、CLI --help、Shell 脚本和测试核实真实入口；文档中的旧命令只能作为
   线索，不能直接认定有效。
3. 检查参考项目的工作树而不只看最后一次 commit，因为最新开发可能尚未提交。
4. 检查当前分支和未提交修改。保留用户已有改动，不覆盖、不重置、不删除无关文件。
5. 先列出项目实际具备的能力、资源依赖、已验证状态和未验证状态，再开始分类。

【目标目录】
README.md                              # 项目首页和最短入口
docs/
├── README.md                           # 全部开发文档总目录
├── capabilities.md                     # 项目能力总表
├── quickstart.md                       # 最短开发环境入口
├── safety.md                           # 全局安全与副作用边界
├── design/
│   ├── README.md                       # 设计文档索引
│   ├── documentation-system.md         # 文档体系和维护规则
│   └── <cross-domain-design>.md         # 跨领域长期设计
└── agent/
    ├── README.md                       # Agent 知识库总入口
    ├── <domain_1>/                     # 每个真实领域完整复制这一结构
    │   ├── README.md                   # 领域导航
    │   ├── charter.md                  # 长期总章程
    │   ├── current.md                  # 当前摘要和纪传体索引
    │   ├── chronicles/                 # 编年体：永久追加
    │   │   ├── README.md               # 编年规则和时间索引
    │   │   ├── YYYY-MM-DD-<stage>.md   # 一个已验证开发阶段
    │   │   └── YYYY-MM-DD-<correction>.md # 后续勘误，不改旧记录
    │   ├── evolution/                  # 纪传体：维护最新事实
    │   │   ├── README.md               # 能力索引和维护说明
    │   │   ├── <capability_1>.md        # 一项长期能力的当前全貌
    │   │   └── <capability_2>.md
    │   └── decisions/                  # 永久架构决定
    │       ├── README.md               # 决定索引
    │       ├── 001-<decision>.md
    │       └── 002-<decision>.md
    ├── <domain_2>/                     # README/charter/current/chronicles/
    │   └── ...                         # evolution/decisions 与上面完全相同
    └── interfaces/
        ├── README.md                   # 接口总索引
        ├── <module-or-service>.md       # Python/API/服务接口
        ├── cli.md                      # CLI 与子命令约定
        ├── data-formats.md             # 数据结构、单位和版本
        ├── local-resources.md           # 本地资源布局和解析规则
        └── external-systems.md          # SDK/设备/外部服务边界

tutorials/
├── README.md                            # 人类教程总入口和阅读顺序
├── environment_setup.md                # 环境安装与重建
├── quickstart.md                        # 最短可运行案例
├── <domain_1>.md                        # 一个领域的基本操作
├── <task_1>.md                          # 一个具体人工任务
├── <task_2>.md
├── recording_and_replay.md              # 项目有录制能力时创建
├── hardware_or_production.md            # 项目有真机/生产操作时创建
└── troubleshooting.md                   # 常见问题、停止和恢复

manifests/
├── README.md                            # 资源清单的格式和恢复说明
└── <resources>.yaml                     # 资源元数据，不存大文件本体

领域名称必须来自“项目领域”参数。例如 simulation、teleoperation、retargeting、real_robot、
data_pipeline、frontend、backend、deployment；不要强行为不存在的领域写空文档。尖括号表示
按项目实际名称替换并可重复创建，不是最终文件名；带“项目有……时创建”的文件按能力选用。

【各类文档的强制职责】
1. docs/agent/README.md
   - Agent 与维护者的总入口。
   - 给出推荐阅读顺序、领域索引、维护规则和暂缓范围。

2. 每个领域的 README.md
   - 只做领域导航。
   - 链接 charter、current、纪传体、编年体和架构决定。

3. charter.md（长期总章程）
   - 记录长期目标、职责边界、依赖方向、安全原则和完成标准。
   - 只写稳定原则，不堆实现细节、最新进度或逐次测试数字。
   - 必须链接 evolution/ 中对应的纪传体；它负责总纲，纪传体负责详细事实。

4. current.md（当前总览）
   - 摘要当前能力、验证状态、已知限制和近期方向。
   - 必须链接 evolution/ 中各项能力的最新纪传体。
   - 只做摘要与索引，不复制纪传体的大段内容。

5. chronicles/（编年体）
   - 按日期记录已经发生且有证据的开发阶段，文件名以 YYYY-MM-DD 开头。
   - 永久保存、只追加、不删除，不因后来方案变化而重写当时事实。
   - 每篇记录当时目标、实际实现、验证证据、当时限制和对后续的影响。
   - 发现旧记录错误时，新增勘误或后续编年记录并链接原文，不静默篡改历史。
   - 不收录原始聊天、无结论调试流水、临时猜测或重复测试输出。

6. evolution/（纪传体）
   - 按长期能力、功能或模块分别建文档，而不是按日期建文档。
   - 始终描述该能力最新、完整、有效的当前事实，是功能级现状的权威来源。
   - 随开发持续更新，允许重写，并删除已经失效、被替代或互相矛盾的旧进展。
   - 包含当前架构、数据流、入口、关键约束、最新验证和已知限制。
   - 历史形成过程通过链接指向 chronicles/，不要在纪传体里复制全部历史。

7. decisions/（架构决定）
   - 一项长期决定一个递增编号文件。
   - 决定永久保存；失效时标记 superseded，并链接替代决定，不能直接删除。
   - 普通 bug、参数微调和一次性实验不要写成架构决定。

8. docs/agent/interfaces/
   - 按模块或稳定边界说明 Python API、CLI、输入输出、单位、资源依赖、依赖方向和安全语义。
   - 区分稳定公开入口、内部实现和高风险实验入口。

9. tutorials/
   - 只面向实际操作者，不要求读者理解 Agent 文档。
   - 按任务组织，写清前提、可复制命令、预期结果、停止方法和常见错误。
   - 明确区分 Shell 脚本、安装后的 CLI、python -m 和直接 Python 文件入口。
   - 真机或生产操作必须从 help、只读检查或 dry-run 开始，危险执行步骤单独标识。
   - 不写迁移历史、Agent 工作流、内部架构争论和测试流水账。

【编年体、纪传体和总章程之间的关系】
- 编年体回答“什么时候发生了什么”，永久保留。
- 纪传体回答“这项能力现在究竟是什么”，始终更新。
- charter.md 回答“这个领域长期遵守什么原则”。
- current.md 回答“现在有哪些能力、证据和限制，并去哪里读详情”。
- charter.md 和 current.md 必须链接纪传体，但不能替代纪传体。
- 纪传体可以链接编年体解释来源；编年体不能被后来的纪传体覆盖或删除。

【轻量化与本地资源】
1. 将模型、纹理、厂商 SDK、录制、数据集、生成结果、日志、缓存和虚拟环境统一放入
   <LOCAL_RESOURCE_DIR>，或通过一个明确环境变量覆盖资源根目录。
2. 在 .gitignore 中忽略这些内容；仓库只提交代码、配置模板、许可说明和资源清单。
3. 用 manifest 记录资源名称、用途、来源、目标相对路径、是否必需和恢复方法；不要提交
   密钥、设备凭证、私有 SDK 或受限数据。
4. 禁止把另一台机器的虚拟环境复制进 Git。记录 Python 版本和重建命令。
5. 清除文档和代码中对旧机器 /home/...、盘符或个人目录的依赖，改用仓库相对路径或参数。
6. 删除、移动或覆盖用户文件前必须确认；不要用破坏性 Git 命令处理已有修改。

【事实与验证规则】
1. 不要虚构命令、路径、模块、测试结果或硬件能力。
2. 明确区分以下证据等级：
   - 文件已迁移；
   - 静态检查或导入通过；
   - 自动测试通过；
   - headless 仿真实际运行通过；
   - GUI/Viewer 人工观察通过；
   - dry-run 或只读设备检查通过；
   - 真机实际运动通过。
3. 旧项目的结果只能写入历史背景。没有在当前项目重新运行，就标为“旧项目曾验证，当前
   尚未复验”，不能冒充当前验收。
4. 真机、生产系统、外部服务和有副作用操作未经明确授权不得连接或执行。
5. 检查 Markdown 本地链接、命令引用、脚本语法、文件存在性、旧绝对路径和 git diff。
6. 代码未改变时无需为整理文档重跑所有昂贵测试，但必须核对相关入口；若改变代码或脚本，
   按风险运行对应测试和 smoke test。

【工作方式】
1. 先给出简短的能力与文档现状，不要一开始创建大量空文件。
2. 从参考资料中提炼有效事实，统一术语、路径和当前入口；不要原样复制旧文档。
3. 先建立各领域 charter/current/evolution/chronicles，再整理 interfaces 和 tutorials。
4. 每个文档只承担一种职责；重复内容改为链接。
5. 未验证或有缺陷的入口必须明确标注，不能因为文件存在就写成“可直接使用”。
6. 保留当前项目已有的合理结构；本模板是职责规范，不要求机械照搬无意义目录。

【Git 权限】
- 可以修改文件：仅当“是否允许修改文件”为 YES。
- 可以本地 commit：仅当“是否允许本地 commit”为 YES。
- 禁止 git push：除非我在本次对话中另行明确说“可以 push”。历史授权不得自动沿用。
- 不执行 force push、reset --hard、清理用户文件或其他破坏性操作，除非我明确指定目标并授权。

【最终交付】
完成后简洁报告：
1. 新建或更新了哪些文档入口和领域；
2. 编年体保留了哪些阶段，纪传体覆盖了哪些当前能力；
3. 哪些大资源已本地化并被 Git 忽略；
4. 实际运行了哪些检查，以及准确结果；
5. 哪些内容仍未验证，特别是 GUI、真机、生产或外部依赖；
6. 是否创建本地 commit及其提交号；
7. 明确说明没有执行 git push，除非本次确实得到授权并执行。

现在请从读取项目开始执行。遇到会改变范围、删除数据、连接真机或产生外部副作用的选择时
先询问；其余可安全验证和整理的工作直接推进。
```
